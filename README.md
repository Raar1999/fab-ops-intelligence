# Fab Ops Intelligence

**A synthetic semiconductor fab whose faults are physics-mediated and whose answer key is a physically separate file — plus the monitors, the root-cause engine and the decision-support layer that read it, and the benchmark that says how often the engine is right.**

The engine is handed one thing: a path to a database. Not the scenario, not the seed, not the fault. What it can and cannot do is measured, published below, and deliberately not flattering.

> ⚠️ **All data is synthetic.** Nothing here is a real-world benchmark, a real fab, or a deployed system. The value on display is the method: an answer-blind analysis stack, and the harness that falsifies it.

## What it does

```
fabsim            a simulated fab: world, timeline, latent state, response,
                  observation, defects, die + yield        — writes both planes
   ├── observable dataset (SQLite, schema v2, 22 tables)   — everything else reads this
   └── truth.json (hidden)                                 — only the evaluator reads this
                    ↓
fabops.semantic   the analytical vocabulary: facts + views, read-only
                    ↓
fabops.monitors   SPC / EWMA / CUSUM, equipment health, normalized yield,
                  defect movers and per-wafer spatial signatures
fabops.diagnosis  diagnose(db_path) → ranked candidates, evidence, rivals,
                  onsets, and `insufficient_evidence` as a first-class answer
fabops.impact     within-product loss, containment ranking
fabops.actions    evidence signature → engineering checks (a data file)
fabops.report     the artifact that carries all of it
                    ↓
fabapp            the product: `fabops-app` — create or load a dataset, explore
                  the fab, investigate it. Orchestrates and presents; computes
                  nothing, and cannot reach the hidden plane
                    ↓
fabeval           the ONE component allowed to hold the answer and the report
                  at once — the benchmark below
```

The separation is the project. `fabsim` writes both planes; `fabops` reads only the observable one; `fabeval` reads both and writes nothing; `fabapp` generates and then analyses, which is what a product does, and may reach neither the hidden plane nor the evaluator. Those four privileges are enforced by import scans, signature scans and runtime invariance tests, not by convention — see [`docs/design/ANTI_LEAKAGE_DESIGN.md`](docs/design/ANTI_LEAKAGE_DESIGN.md) and [ADR-037](docs/ARCHITECTURE_DECISIONS.md).

### Measured capability

Every number below is produced by `fabops-benchmark` and rendered by `publish_readme.py`; none of it is typed by hand, and a test fails if this section and the committed results disagree. Engine `fabops.diagnosis/1.1.0`, statistic `own_scale_step`, abstention level α = 0.05, 2000 permutations, anchor at [0.5] of the horizon.

| | development (8 scenarios x 3 seeds) | held-out (4 scenarios x 5 seeds) | library (12 scenarios, both roles) |
|---|---|---|---|
| datasets | 24 (21 faulted) | 20 (15 faulted) | 44 (36 faulted) |
| false-alarm rate | 0.000 | 0.000 | 0.000 |
| detection rate | 0.000 | 0.000 | 0.000 |
| attribution, rank 1 | 0.095 | 0.000 | 0.065 |
| attribution, top 3 | 0.190 | 0.000 | 0.129 |
| mean reciprocal rank | 0.228 | 0.075 | 0.179 |
| median onset error (days) | 7.0 | 10.0 | 7.0 |

- **development (8 scenarios x 3 seeds)** — 8 scenario(s); **not a capability claim**: measured on 8 scenario(s); a capability claim needs at least 10 (EXPANSION_ROADMAP Phase 6), so this is a measurement on a named population and not a claim about the system. the method was selected on this population; these numbers describe the fit, not the capability
- **held-out (4 scenarios x 5 seeds)** — 4 scenario(s); **not a capability claim**: measured on 4 scenario(s); a capability claim needs at least 10 (EXPANSION_ROADMAP Phase 6), so this is a measurement on a named population and not a claim about the system. scored with the anchor rule, statistic and level frozen beforehand
- **library (12 scenarios, both roles)** — 12 scenario(s); a capability claim is permitted on this population. development and held-out pooled; the split is reported separately above because a development number describes the fit and a held-out one describes the capability

**What those numbers mean, stated plainly.** At its declared level the engine **abstains on every dataset this project can build** — its detection rate is zero and so is its false-alarm rate, which is the half of its contract it keeps exactly. It ranks a planted entity first on about one development dataset in ten and on none of the held-out ones. That is weak, it is measured, and it is reported here rather than in a footnote: every lever that would buy detections — a multi-anchor grid, a pooled-denominator statistic, a higher level — was built and measured, and each one spends calibration this architecture ranks above power (ADR-031 §12).

The claim this repository makes is therefore not *"it finds the fault"*. It is: **a synthetic fab whose faults are physics-mediated and whose answer key is a physically separate file, an engine that is handed a database path and nothing else, and a benchmark that says exactly how often it is right.** The third of those is what most portfolio projects are missing, and it is the one that makes the first two checkable.

**Library coverage**, measured from the scenario configurations rather than asserted: confounded ×2, events ×3, grain ×3, mechanism ×5, onset_band ×4, profile ×4, severity ×4, tool_type ×5.

## Getting started

```bash
git clone <this repository> && cd fab-ops-intelligence
pip install -e ".[app,notebook,dev]"

fabops-app
```

That is the whole of it. `fabops-app` opens a local browser application and
lands on **Datasets**, because there is deliberately no default one — the
legacy database below is a different fab, and a product that quietly fell back
to it would answer the wrong question with no error anywhere.

```
Datasets ─── pick a scenario and a seed ──► generate (~20 s) ──┐
        └─── or open one that already exists ──────────────────┤
                                                               ▼
   Fab Today · Process · Equipment · Yield · Defect · Wafer explorer
                                                               │
                                                               ▼
   Investigation ── run the engine ── ranked candidates or insufficient
                    evidence ── evidence, onsets, cross-family agreement,
                    confounders, rivals considered, what could not be
                    assessed ── "assume it is this one, what would acting
                    cost?" ── export
```

Nothing in that path needs a file path, a dataset id, a scenario file or a
Python command. The **Datasets** page shows what each dataset is — scenario,
seed, horizon, schema and generator version, build fingerprint, validation
status — and refuses anything that is not a schema v2 dataset, saying which of
the four things went wrong.

On every dataset this project can build, the Investigation page reports
**insufficient evidence** — correctly, and this is the interesting part,
because at its declared level the engine does not clear its own bar. It then
shows, per candidate, exactly which criteria were met and which were not, with
the number from the artifact behind each one. A product that hid that would be
answering the question before the engine did.

Because the engine names no subject, impact and containment would be empty on
every screen, so the page also lets an engineer say *assume it is this one* and
asks what acting on it would cost — exposed wafers, the deficit against
same-role peers, the lots to contain first, the checks to run. The exported
artifact records that the subject was **supplied** rather than concluded, which
is a different claim and is kept as one.

Useful flags: `--dataset` and `--page` open on a particular screen,
`--list` prints the datasets that exist, `--where` prints the paths this
installation uses, `--check` runs the whole workflow headlessly, and
`--legacy` starts the legacy dashboard described below.

## For developers: the commands underneath

The product is a thin layer over the same functions the command line exposes,
and those remain the testing and scripting surface:

```bash
fabops-diagnose  data/scenarios/<dataset>/fab.db   # the engine alone, as JSON
fabops-monitor   data/scenarios/<dataset>/fab.db   # the four monitor families
fabops-report    data/scenarios/<dataset>/fab.db --summary   # the full artifact
fabops-benchmark --population both                 # build a population, score it

fabops-app --check      # discover → open → 7 pages → diagnose → export, headless
make dataset SCENARIO=chamber_edge_uniformity SEED=42   # one dataset, no browser
```

## The legacy demo, and why it is still here

Alongside all of that, this repository still contains its own predecessor: a
schema **v1** database and a narrated ETCH-02 investigation whose conclusion is
a documented constant (`fabops.config.DEMO_SUSPECT_TOOL`).

```bash
python -m fabops.build_db          # or: fabops-build
python -m fabops.investigation     # or: fabops-investigate
fabops-app --legacy                # or: streamlit run app/ops_dashboard.py
```

It is kept deliberately, under [ADR-010](docs/ARCHITECTURE_DECISIONS.md): it is
the project's regression anchor, it reads a different fab from everything
above, and nothing has replaced it *on that surface*. It is a **demonstration
RCA, not a discovery engine** — it narrates and verifies a planted answer. The
forensic audit of exactly how it reaches that answer is in
[`docs/audit/RCA_AUDIT.md`](docs/audit/RCA_AUDIT.md), and the whole of the work
above exists because of what that audit found.

It is reachable *from* the product and is not merged *into* it, which is the
same decision made twice: one application with one navigation bar answering
about two different fabs is the legacy/v2 confusion this architecture spends
its guards avoiding. And the two verbs stay separately named so that typing the
obvious command cannot hand somebody the hard-coded story while they believe
they ran the engine: `fabops-investigate` is the demo, `fabops-diagnose` is the
engine.

## Design notes

- **Answer-blindness is structural, not a promise.** The kill model is not
  *shown* the hidden plane — `probe(timeline, observations, population)` has no
  parameter it could arrive through. The emitter is a serializer that draws no
  random numbers. The engine takes a database path, not a directory, because a
  directory has `truth/` as a sibling. Each of those is a signature, and each has
  a test that fails if the signature widens.
- **Logic lives in SQL.** The v2 semantic layer is a `.sql` file of views,
  installed read-only so that reading a dataset cannot change the bytes a
  manifest hashes. The v1 layer is 13 named views in `sql/views.sql`.
- **Every threshold is measured against the distribution of its own statistic.**
  Five separate gates of this project have each found a criterion whose
  reference distribution had never been computed — four of them inherited from
  the v1 demo (ADR-026 through ADR-030), and one written by this project itself
  and caught the same way (ADR-033). The rule that came out of it: a criterion
  phrased as "the demo should visibly show X" must ship with the distribution of
  X on a fault-free world before it may gate anything.
- **Determinism is a property, not a habit.** Same inputs, same content hash;
  every multi-row query states a total order; and a harness that shuffles the
  rows of any query without an `ORDER BY` must leave every report byte-identical.
- **The product knows which scenario you picked; the engine does not, and that
  is measured rather than promised.** The application has to know — you chose
  it — so the interesting question is whether that knowledge can reach the
  analysis. It cannot: generation returns a handle with no field the answer
  could arrive through, the analysis path takes a database path and nothing
  else, and a test renders one dataset's investigation twice — once with the
  scenario resolvable and once with it not — and requires the two to be
  byte-identical. The scenario picker itself publishes five build inputs and
  withholds the prose and the event counts, because both are the answer.

## Limitations — kept brutal

- **The engine is weak.** At its declared level it abstains on every dataset in
  the library. Its false-alarm rate is exactly zero and so is its detection rate.
  The numbers above are the whole claim.
- **It can only name entities in two of eight equipment families.** Every
  statistic is a standing among same-role peers and needs at least two of them,
  so 13 of this world's 24 chambers are `not_assessable` in every dataset this
  project can build. The engine says so with a reason; it is a structural
  boundary, quantified in `DIAGNOSIS_CONTRACT.md` §8.2.
- **"Root cause" here means entity attribution, not mechanism identification.**
  No observable channel identifies which mechanism acted — a defect class is a
  noisy draw over a hidden origin, a tester bin a symptom drawn over a hidden
  cause — so an engine that named a mechanism would be matching a catalogue.
- **The monitors' signal rate is above nominal and published as such** (0.0060
  per charted point against a declared 0.0027, on twelve fault-free worlds; the
  same chart reads 0.94× nominal when its spread is well estimated, so what is
  left is the price of a twelve-day baseline). A monitor signal is a prompt to
  look, not a claim, and a signal *count* is not attribution — measured, in
  `fabops.monitors`.
- **One fab, one route, ~500 wafers per dataset, no sensor traces, simulated
  physics.** The scale ceiling is declared rather than apologised for (ADR-012).
- **Nothing here has been deployed anywhere, and no number in this repository
  describes a real fab.**

## Testing and reproducibility

```bash
pytest -q            # the full local suite
fabops-app --check   # the product workflow, end to end, without a browser
```

A dataset is fully determined by (scenario config hash, world hash, seed,
fabsim version, schema version) — all five recorded in its manifest, and the
identity is a canonical row-level content hash rather than the bytes of a
SQLite file, so it is portable across platforms. A reference-build table pins
the digest each generator version produces, so generation cannot move without a
version number moving with it.

Continuous integration is **not** currently exercised: the workflow in
`.github/workflows/` encodes the locally verified sequence, and every check
described here is run locally.
